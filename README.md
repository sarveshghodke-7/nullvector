# AI Defense Lab for Payment Security

> **Mastercard Innovation Challenge @ GFF 2026**
> **Red Team → Generate → Detect → Evaluate → Feedback**

An end-to-end AI-powered payment security laboratory that identifies emerging GenAI-enabled fraud attacks, generates high-fidelity synthetic attack scenarios, detects them using specialized AI/ML defenses, evaluates detection performance, and feeds missed attacks back into the attack-generation pipeline to continuously harden the defense.

---

# 1. Project Overview

Generative AI has lowered the cost and complexity of sophisticated payment fraud.

Attackers can now use AI to:

* Create convincing synthetic identities
* Generate realistic KYC artifacts
* Automate social engineering
* Clone voices and manipulate video
* Create fake merchants and invoices
* Generate large volumes of realistic fraudulent behavior
* Search for weaknesses in AI-powered fraud detection models

Traditional static rules and fixed fraud models struggle against attacks that are adaptive and continuously changing.

Our solution approaches this as an **AI Red Team / Blue Team problem**.

Instead of building only a fraud detector, the system continuously:

```text
IDENTIFY
   ↓
GENERATE
   ↓
DETECT
   ↓
EVALUATE
   ↓
FEEDBACK
   ↺
GENERATE HARDER ATTACKS
```

The central idea is:

> **The attacks generated by the Red Team become the training and stress-testing ground for the Blue Team.**

---

# 2. Problem Statement

The challenge asks us to build a single end-to-end Red Teaming AI system capable of:

1. **Identifying** novel and emerging GenAI-powered payment fraud attacks.
2. **Generating** realistic simulations of those attacks at scale.
3. **Defending** against the generated attacks using accurate AI/ML detection.
4. **Learning from failures** so that attacks missed by the defense can be used to generate harder variants.

The solution is evaluated on:

* Diversity of attacks identified
* Fidelity of attack simulation
* Detection efficacy
* Novelty
* Real-world feasibility in live payment environments

# 4. Selected Attack Categories

Our initial implementation focuses on four major attack families.

| Attack                        | Primary Target             | Main Data Type                      | Primary Defense                  |
| ----------------------------- | -------------------------- | ----------------------------------- | -------------------------------- |
| Synthetic Identity Fraud      | Customer onboarding / KYC  | Documents + tabular behavior        | XGBoost                          |
| Deepfake Voice / Video        | Authentication / Video KYC | Audio + video                       | Pretrained deepfake models       |
| Adversarial Perturbation      | Fraud detection model      | Tabular transactions                | XGBoost + adversarial retraining |
| Fake Merchant / Invoice Fraud | Merchant onboarding        | Documents + web + merchant behavior | Merchant risk model              |

The Identify pillar may document a broader taxonomy of emerging attacks, while the implementation focuses on these selected attack families.

# 5. System Principles

## 5.1 One Orchestrator

The orchestrator controls the workflow.

Attack modules contain attack-specific logic.

The orchestrator should **not** implement the internals of each attack.

---

## 5.2 Common Contracts

Every attack module must communicate using common schemas.

```text
Identify Output
      ↓
Generate Input
      ↓
Generate Output
      ↓
Detect Input
      ↓
Detect Output
      ↓
Evaluate
      ↓
Feedback
```

---

## 5.3 JSON Is the Control/Communication Layer

JSON is used for:

* Attack definitions
* Configuration
* API requests
* API responses
* Module-to-module metadata
* Metrics
* Feedback instructions

JSON is **not** the primary storage format for large transaction datasets.

---

## 5.4 Tabular Data Is the ML/Data Layer

Structured payment/customer/merchant data is stored using:

* CSV
* Parquet
* SQLite

depending on the use case.

---

## 5.5 Media Is Stored as Files

Documents and media are stored separately:

* PNG/JPG → images
* PDF → documents
* WAV → audio
* MP4 → video

# 8. Module Responsibilities

| Module         | Responsibility                            | Must Not Do                                  |
| -------------- | ----------------------------------------- | -------------------------------------------- |
| `identify`     | Define structured attack specification    | Generate large datasets                      |
| `generator`    | Generate attack artifacts                 | Train detection models                       |
| `simulator`    | Simulate behavior/lifecycle               | Manage frontend                              |
| `detector`     | Detect attacks/fraud                      | Generate attacks                             |
| `evaluator`    | Calculate metrics                         | Own orchestration                            |
| `feedback`     | Analyze failures and initiate improvement | Directly control frontend                    |
| `orchestrator` | Control pipeline execution                | Implement attack-specific algorithms         |
| `schemas`      | Define communication contracts            | Contain business logic                       |
| `api`          | Expose backend endpoints                  | Implement attack algorithms                  |
| `llm`          | Centralize LLM interaction                | Be independently initialized by every module |
| `storage`      | Manage datasets/artifacts/results         | Implement ML logic                           |

# 23. Attack 3 — Adversarial Perturbation

## Objective

Generate fraudulent transaction feature combinations that cause the fraud model to classify the transaction as legitimate.

The attacker is targeting the **model's learned decision boundary**, not basic arithmetic.

## Input

A transaction dataset and a trained fraud classifier.

Example:

```text
amount
timestamp
merchant_category
device_age
location_distance
transaction_velocity
...
```

## Workflow

```text
Existing Fraud Transaction
        ↓
Baseline Fraud Model
        ↓
Fraud Probability
        ↓
Perturbation Engine
        ↓
Generate Candidate Variants
        ↓
Apply Realism Constraints
        ↓
Score Candidates
        ↓
Find Evasive Transaction
        ↓
Run Blue-Team Detector
        ↓
Measure Attack Success Rate
        ↓
Extract Successful Evasions
        ↓
Adversarial Retraining
        ↓
Evaluate Again
```

## Important distinction

The original transaction remains unchanged.

The attack generator creates a **new derived transaction**.

```text
Original:
T001 → Fraud → score 0.97

Adversarial variant:
ADV001 → Fraud → score 0.42
```

The ground-truth label remains:

```text
fraud_label = 1
```

even if the model predicts:

```text
prediction = 0
```

That is a false negative and therefore a successful evasion.

## Potential generation strategy

Prototype approach:

**Constraint-based search / optimization**

Possible constraints:

* Amount change within realistic range
* Merchant category preserved or plausibly changed
* Transaction timing remains realistic
* Location changes remain plausible
* Device behavior remains consistent

## Important metric

**Attack Success Rate**

```text
Successful evasions
-------------------
Total adversarial attempts
```

This should be reported in addition to precision, recall and F1.

# 25. LLM Usage Strategy

LLMs should be used selectively.

The system should **not call an LLM for every generated record**.

## Appropriate LLM usage

| Task                            | LLM              |
| ------------------------------- | ---------------- |
| Attack ideation                 | Yes              |
| Attack specification            | Yes              |
| Synthetic personas              | Limited / cached |
| Attack strategy generation      | Yes              |
| Fake business descriptions      | Limited          |
| Invoice text                    | Limited          |
| Hard-example generation prompts | Yes              |
| Transaction amounts             | No               |
| Random names                    | No               |
| Random addresses                | No               |
| Large transaction datasets      | No               |
| XGBoost prediction              | No               |
| Evaluation metrics              | No               |

# 26. LLM Architecture

All LLM access should go through:

```text
backend/llm/client.py
```

Attack modules should **not** independently create API clients.

```text
Attack Module
      │
      ▼
LLM Client
      │
      ├── Provider
      ├── API key
      ├── Rate limiting
      ├── Retry
      └── Cache
```

This allows the project to:

* Change providers
* Reduce API usage
* Cache responses
* Work with free tiers
* Disable LLM calls during testing
* Use local/static templates

# 27. API Usage Minimization

The prototype should prefer:

```text
LLM
 ↓
Generate strategy/template
 ↓
Cache result
 ↓
Python/Faker/statistical simulator
 ↓
Generate thousands of variations
```

instead of:

```text

 ↓
10,000 API calls
 ↓
```

The latter is unnecessary and will quickly exhaust free-tier limits.

```text
        │                 │                 │
```

# 30. Evaluation Metrics

The system should report metrics separately for each attack.

## Confusion Matrix

|              | Predicted Legit | Predicted Fraud |
| ------------ | --------------: | --------------: |
| Actual Legit |   True Negative |  False Positive |
| Actual Fraud |  False Negative |   True Positive |

---

## Precision

Of everything classified as fraud, how much was actually fraud?

```text
Precision = TP / (TP + FP)
```

---

## Recall

Of all actual fraud, how much was detected?

```text
Recall = TP / (TP + FN)
```

---

## F1 Score

Harmonic mean of precision and recall.

```text
F1 = 2 × Precision × Recall
          ------------------
          Precision + Recall
```

---

## AUC-ROC

Measures the model's ability to separate fraud from legitimate transactions across different thresholds.

---

## False Positive Rate

Measures legitimate transactions incorrectly flagged as fraud.

This is particularly important for payment systems because excessive false positives negatively affect legitimate customers.

---

## Attack Success Rate

For adversarial attacks:

```text
Successful Evasions
-------------------
Total Attack Attempts
```

Lower is better for the defense.

# 31. Feedback / Learning Loop

The system does not require one universal AI model.

Instead, each detector can improve using attack-specific feedback.

```text
                 GENERATE
                    │
                    ▼
                  DETECT
                    │
                    ▼
                EVALUATE
                    │
          ┌─────────┴─────────┐
          │                   │
     Correctly Detected    False Negative
                              │
                              ▼
                       Analyze Failure
                              │
                              ▼
                    Generate Hard Variant
                              │
                              ▼
                       Add to Dataset
                              │
                              ▼

                              │
                              ▼
                         Detect Again
```

# 32. Learning by Attack

## Synthetic Identity

False negatives become examples of identities whose behavioral patterns were too realistic.

Feedback can generate harder:

* Identity combinations
* Device patterns
* Transaction histories
* Credit-building behavior

The tabular detector is retrained.

---

## Deepfake

Missed samples can be analyzed for:

* Compression
* Lighting
* Audio quality
* Face pose
* Background
* Noise

New augmented samples can be introduced and the detector retrained.

---

## Adversarial Perturbation

Successful evasions become adversarial training examples.

```text
Fraud
 ↓
Perturb
 ↓
Evade model
 ↓
Store adversarial sample
 ↓
Retrain
 ↓
Evaluate attack success rate again
```

This is the strongest example of the closed-loop Red Team / Blue Team concept.

---

## Fake Merchant

Missed merchants can be used to generate harder variants with:

* More realistic business history
* Better transaction behavior
* More credible invoices
* More consistent metadata
* More realistic storefronts

The merchant detector is retrained.

# 46. Architecture Summary

The final architecture can be summarized as:

```text
                     ┌──────────────────┐
                     │     IDENTIFY     │
                     │ Attack Knowledge │
                     └────────┬─────────┘
                              │
                              ▼
                     ┌──────────────────┐
                     │     GENERATE     │
                     │ Red Team Engine  │
                     └────────┬─────────┘
                              │
                              ▼
                     ┌──────────────────┐
                     │      DETECT      │
                     │  Blue Team AI    │
                     └────────┬─────────┘
                              │
                              ▼
                     ┌──────────────────┐
                     │     EVALUATE     │
                     │ Metrics/Results  │
                     └────────┬─────────┘
                              │
                              ▼
                     ┌──────────────────┐
                     │     FEEDBACK     │
                     │ Hard Examples    │
                     └────────┬─────────┘
                              │
                              └──────────────► GENERATE
```

The key engineering principle is:

> **The orchestrator owns the workflow, attack modules own attack-specific logic, schemas define communication contracts, datasets hold structured behavioral data, files hold media artifacts, and the feedback layer converts detection failures into the next generation of attacks.**

# 48. Important Project Philosophy

This project should not be presented as:

> "We built four fraud detectors."

It should be presented as:

> **"We built an adversarial AI security laboratory for payment systems in which attack intelligence drives attack generation, generated attacks stress-test specialized defenses, and defense failures automatically become the next generation of red-team scenarios."**

That distinction is central to the architecture and to the challenge's emphasis on the closed-loop Identify → Generate → Defend concept.
